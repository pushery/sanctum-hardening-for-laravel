# Changelog

All notable changes to `pushery/sanctum-hardening-for-laravel` are documented here. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

A release carries only the sections that have an entry, in this order: `### ⚠️ Breaking`, `### ✨ Added`, `### 🔧 Changed`, `### ⚡ Performance`, `### 🐛 Fixed`, `### 🔒 Security`, `### 🧹 Deprecated`, `### 🗑️ Removed` and `### 📚 Documentation`.

## [0.9.0] - 2026-11-24

### ✨ Added

- **An export or a deletion of an account finds its rows in the package's tables through a public method.** `SanctumHardening::storedKey()` gives a token's or a holder's key as the string the tables store it under, in `token_id`, `tokenable_id`, `revoked_by_id` and `rotated_by_id`. **Upgrade:** it replaces `TokenPrefixes::key()`, which 0.8.0 removed while its successor stayed internal.
- **A model that holds tokens can refuse a new one, on every way to a token.** A model that implements `RefusesNewTokens` is asked before a token is written, by `mint()`, `mintFor()` and `mintForSystem()` of `PersonalTokens`, by a rotation, by the screen and by `createToken()` of `HasApiKeys`, with the name, the abilities and the expiry of the new token. A sentence it returns refuses the token as a `MintRefused` with the reason `refused_by_holder` and the sentence in `refusal`, and the screen shows the sentence. A refused token costs neither the minute nor the confirmation of a password that covers one mint. **Upgrade:** since 0.8.0 the package writes a key itself and calls no `createToken()` of the model, so an override of `createToken()` that refuses a token refuses only the calls of the application's own code. Such a refusal moves into `refusalOfANewToken()`.

### 🔧 Changed

- **A token over its limit gets the JSON:API error `rate_limited` of http-api where that package answers the request.** With `pushery/http-api-for-laravel` installed and its errors switched on, a throttled request of the API is answered as an error document with the code `rate_limited`, `Retry-After` and the limit headers, the answer the gateway gives for the same limit. The package answered with a response of its own before, which a client of a JSON:API could not read as an error object. Without http-api, or on a request it does not answer, the response stays as it was.

### 🐛 Fixed

- **The list of tokens fits a phone in the WireKit view.** Below the `md` breakpoint it stacks each token into a card of its own, its Rotate and Revoke buttons at the foot. On a phone the abilities, the expiry, the last use and both buttons stood outside the screen, and the table scrolled sideways in its frame. WireKit stacks a table from 2.70.0 on, and an older one keeps the table as before.
- **A token's Rotate and Revoke buttons keep their distance in the WireKit view.** In a narrow last column of the token list the two wrapped onto two lines and stood against each other. They now sit in a row with a gap, which they keep when they wrap.
- **The commands print a token's name, its abilities and the values they read as they are written.** Symfony's console formatter read a part of a value that looks like a style tag, such as `<info>` or `</>`, as styling and dropped it: in the name or an ability of a token, a guard name, a time zone the database session reports, or a value of the configuration. `sanctum-hardening:doctor`, `sanctum-hardening:prune-prefixes`, `sanctum-hardening:prune-revocations`, `sanctum-hardening:prune-uses` and `sanctum-hardening:send-alerts` escape what they print.
- **The days and hours a token has left read in the plural in a regional locale.** Each form of the lines for days and hours names its count, `{1} :count day|[2,*] :count days`, in all seven catalogs. Laravel picks a form without a count by the name of the locale, from a table that knows `de_AT` but no locale written with a hyphen, so an application on `de-AT` showed the singular for 30 days.

### 📚 Documentation

- **The documentation says that the `octane` store of Laravel Octane is out of the pruner's reach.** The store keeps an expired entry in a table of a fixed number of rows, `octane.cache.rows`, until its key is written again or the server restarts, and the scheduler, where the pruner runs, sees an empty store. Once the table is full, writing a new key fails, so the documentation advises against making `octane` the default cache store of an application that runs this package.
- **The documentation of a token's networks and of the throttle says where a visitor can claim another address.** The minting page promised that a client cannot claim an address it does not send from, which holds from `laravel/framework` 13.43.0 on. Below it, an application that configures no trusted proxy and whose web server answers any host name takes a header the visitor sends as the mark of a Forge or Vapor proxy (GHSA-559m-v249-7qw2): a token limited to its networks then passes from any address the visitor claims, and a request nobody is signed in for starts a count of its own with each one. Both pages name the framework update, trusted proxies and a web server that answers only the application's host names as the ways to close it.

## [0.8.0] - 2026-11-22

### ⚠️ Breaking

- **Every token the package mints is a key in a format of its own, and Sanctum's `<id>|<text>` no longer authenticates.** A key reads `<product>_<environment>_<id>_<secret><checksum>`: a prefix that tells a person and a secret scanner what the key belongs to, a public identifier of 12 characters, a secret of 43 characters and a CRC-32 checksum in base 62. Sanctum's `token` column holds the SHA-256 of the whole key. The package sets `SanctumHardeningPersonalAccessToken` as Sanctum's token model, which reads the form and the checksum before it asks the database and then finds the token by its identifier, so a mistyped key and a value of Sanctum's own form cost no query. **Upgrade:** every token minted before this release stops working and is minted again. A model whose tokens the application's own code mints with `createToken()` uses `HasApiKeys` in place of Sanctum's `HasApiTokens`, and an application that sets a token model of its own uses `FindsTokensByKey` on it. The release adds a migration for the table `sanctum_hardening_key_ids`; where the migrations are published, copy `2026_11_21_000000_create_sanctum_hardening_key_ids_table.php` from `vendor/pushery/sanctum-hardening-for-laravel/database/migrations` into `database/migrations` and run `php artisan migrate`.
- **The screen, the mails and the record of a revocation name a token by the start of its key.** They named it by the first twelve characters of its secret, kept in `sanctum_hardening_token_prefixes`, and now name it by the characters its key starts with, up to and including the identifier, which give away nothing of the secret. `TokenRevocation` carries them as `keyPrefix`. `TokenPrefixes` is gone: `of()` of `KeyIds` gives the prefixes of the given tokens and `idsOf()` their identifiers. `sanctum.token_prefix` no longer applies to the tokens the package mints. **Upgrade:** the table `sanctum_hardening_token_prefixes` is no longer read or written, and an application that wants it gone drops it with a migration of its own. A mail sent before the release names the old prefix. An export of an account's data that read the old table reads `of()` of `KeyIds`.

### ✨ Added

- **`keys.product` and `keys.environment` set the prefix of every key.** The product is 2 to 10 letters a-z and the environment `live` or `test`, read from `SANCTUM_HARDENING_KEY_PRODUCT` and `SANCTUM_HARDENING_KEY_ENVIRONMENT`. Unset, the letters of `app.name` stand in for the product, cut to ten, and the environment is `live` where `app.env` is `production` and `test` everywhere else. A value a key cannot name refuses the mint with the setting named.
- **`KeyFormat` reads and issues keys for code of an application's own.** `KeyFormat::parse()` gives a key's product, environment, tenant and identifier, or null for a value that is no key, `KeyFormat::refusal()` the first rule a value breaks, `KeyFormat::fingerprint()` the `sha256:` fingerprint of the whole key, and `KeyFormat::PATTERN` the pattern a secret scanner finds a key by.
- **The limiter reads a holder's limits from a tier the application gives.** `ResolvesThrottleTier` gives the `ThrottleTier` of a holder, a user or the workspace a token was minted for: a `ThrottleCounter` for each token, one for the holder over all of its tokens, or both, each with the requests a minute, the most requests in one second, a budget of writes for every request with a method other than `GET`, `HEAD`, `OPTIONS` and `TRACE`, where `0` refuses every write, and a burst. The limiter asks on every request it counts, so a changed tier counts at once. Unbound, and for a holder it gives no tier, `throttle.*` is the tier, counted under the keys and with the numbers of before, so an application without tiers notices nothing. The quickstart of the screen names the rates of the holder's tier. **Upgrade:** nothing changes for an application without tiers; `throttle.per_token`, `throttle.per_user` and the two bursts now name the tier every holder without one counts against.
- **`PruneExpiredCacheKeys` also prunes behind a `failover` store and a `storage` store.** Both of these Laravel cache drivers leave expired entries behind as a database or a file store does. A failover store writes each entry into the first of its stores that answers, so the pruner goes through each of its stores once. A storage store lays its files out on a filesystem disk the way a file store does in its directory, and the pruner deletes the expired files the store laid out there and leaves every other file on the disk alone.

## [0.7.0] - 2026-11-21

### ✨ Added

- **`sanctum-hardening:doctor` names a database or a file store whose expired cache keys nothing prunes.** Where the default store or the store in `cache.limiter` is a database or a file store, which keeps an expired key until it is read again, and no entry of the scheduler calls `PruneExpiredCacheKeys` by its class, the doctor says so and ends with exit code 1. A server that prunes outside the scheduler, or schedules the call under a name of its own, names `prune-cache-keys` with `--scheduled-elsewhere`.
- **The screen offers a choice of overlap for a rotation.** Where `rotation.overlaps` lists overlaps in hours, `[1, 24, 168]` for an hour, a day or a week, a field above the list of tokens offers them beside `rotation.overlap_hours`, which is preselected for every rotation, and the rotate button asks with the overlap chosen. The screen refuses an overlap it did not offer. Without the list it rotates with `rotation.overlap_hours` as before. The question names the overlap in days where it is whole days, so the default reads as one day rather than as 24 hours; a published copy of the translations that names `:hours` keeps working.
- **The quickstart of the screen names the limits an application gives it.** It named `throttle.per_token` and `throttle.per_user` on every screen, also where the API runs behind a limiter of the application's own, a plan's for instance, and there it named limits the API does not have. Bind `Pushery\SanctumHardening\Throttling\ResolvesQuickstartLimits`, and the quickstart names what its `limitsFor()` gives for the holder of the screen, the user or a workspace. A null leaves its part of the sentence out, and two nulls leave out the sentence. Unbound, the quickstart names the limits of the package's limiter, as before. A host that published the views takes the sentence from the new `$quickstartLimits`; `$perToken` and `$perUser` still carry the numbers.

### 🔧 Changed

- **`PruneExpiredCacheKeys` clears a file store as well.** Beside the expired rows under `sanctum-hardening:` in a database store, it now deletes the expired files of a file store, which names its files by a hash of the key and so cannot tell the package's from the application's; the store already treats each of them as missing. Redis, Memcached and every other store that expires entries itself stay untouched. The call in the schedule stays `Schedule::call(PruneExpiredCacheKeys::class)->daily();`.

### 🐛 Fixed

- **The quickstart names the limits the limiter counts with.** Where `throttle.per_token` or `throttle.per_user` held no whole number of one or more, the limiter counted with 60 or 120, while the quickstart named the setting as it stood. It names the 60 and the 120 now.

### 📚 Documentation

- **The Boost skill declares its example of the token model in `App\Models`.** The class `User` that uses Sanctum's trait stood in no namespace there, so a copy of it was a global class the application never binds. It now reads as the same example on the documentation's start page.

## [0.6.0] - 2026-11-20

### ⚠️ Breaking

- **Sanctum asks no session guard before it reads a bearer token, unless the application names one.** The package sets `sanctum.guard` to the new `sanctum-hardening.session_guards`, an empty list by default, and a `guard` in `config/sanctum.php` has no effect. An application whose single-page client signs in over the session through Sanctum's `statefulApi()` names its guard there, `['web']` for one.

### 🔒 Security

- **A raw remember cookie no longer signs in to the API.** With Sanctum's default guard `web`, a route without a session, as in the `api` group, took the remember cookie as it came for a login, so whoever could read a user's `remember_token`, from a backup or a replica for instance, reached the API with every ability and without the application key. Now only a bearer token signs in, and `sanctum-hardening:doctor` reports a guard in `sanctum.guard` while no route runs behind `EnsureFrontendRequestsAreStateful`.

## [0.5.0] - 2026-11-20

### ✨ Added

- **An ability can be for one kind of holder alone.** An entry of `abilities` takes a label and `holders`, the morph classes or class names that may carry it. The screen offers it to those holders alone, and `mint()` and `mintFor()` refuse it for another with the reason `holder`. An entry without `holders` is for every holder, as before.
- **A token or a user can send a burst above its rate.** `throttle.burst_per_token` and `throttle.burst_per_user` (`SANCTUM_HARDENING_BURST_PER_TOKEN`, `SANCTUM_HARDENING_BURST_PER_USER`) name the most a holder that was quiet may send at once, and the window grows to fit: with `per_token` 300 and `burst_per_token` 600, a token sends up to 600 in two minutes, 300 a minute on average. Unset, the limits are what they were.
- **A token can be rotated, with an overlap.** `PersonalTokens::rotate()` and a button on the screen give a token a successor with its name, abilities, networks and lifetime, and let the old one work for `rotation.overlap_hours` hours more (`SANCTUM_HARDENING_ROTATION_OVERLAP_HOURS`, 24 by default), so whatever still calls with the old key has time to take the new one. The screen says until when a replaced token works, and the expiry alert names that end before it comes. A new table, `sanctum_hardening_token_rotations`, keeps which token replaced which.

  **Upgrade:** the release adds a migration. Where the migrations are published, copy `2026_11_15_000000_create_sanctum_hardening_token_rotations_table.php` into `database/migrations` and run `php artisan migrate`.

- **`sanctum-hardening:doctor` names a prune that does not run.** It names each daily command of the package that nothing in Laravel's scheduler runs, `sanctum-hardening:send-alerts` only while an alert is switched on, and the rows a prune should have deleted: requests recorded longer ago than `usage.keep_days` and tokens revoked longer ago than `revocations.keep_days`, each a day after the retention. Either ends the command with exit code 1, so a prune that never runs, or fails every night, no longer keeps those rows for good without a word. `--scheduled-elsewhere` names a command the server runs outside the scheduler, from a cron line for instance.

  **Upgrade:** a deploy step that runs the doctor fails where the schedule lacks one of these commands. Schedule it daily, switch both alerts off where `send-alerts` is not wanted, or name a command a cron line runs with `--scheduled-elsewhere`.

- **The screen leaves out its heading where the page heads it.** A page with a header of its own showed "API tokens" twice, as its own heading and right under it as the screen's, with the screen's sentence under that. `<livewire:sanctum-hardening.tokens :heading="false" />` leaves out the screen's heading and the sentence; the screen keeps its name for a screen reader, the heads of its parts stand one level under the page's heading, and once the last token is revoked the focus moves to the screen. Without the parameter the screen shows both as before. A host that published the views takes the parameter from the views of the package.
- **The screen hands over a new token with a button that copies it, and in a field the keyboard selects.** The token a mint shows once stood as text under the status line, with nothing that copied it, and text on a page is selected from the keyboard only with caret browsing, which Safari does not have. The token now stands right after the form, where the next Tab goes from the button that created it, in a read-only field that Ctrl or Cmd and A select whole, named by the new line `screen.new_token`. In the WireKit view a button beside the field copies the token and announces that it did. A host that published the views takes the field from the views of the package.
- **`PruneExpiredCacheKeys` deletes the package's expired keys from a database cache store.** A database store deletes the row of an expired key only when that key is read again, and nothing in Laravel prunes its table, so the mark of every confirmation a mint spent, the mark that holds back a second record of the same use of a token, and the counts of mints and of wrong passwords of a holder who stopped stayed in the table for good. Scheduled once a day with `Schedule::call(PruneExpiredCacheKeys::class)->daily()`, it deletes the rows of the package's expired keys from the default store and from the store in `cache.limiter`, a thousand to a statement, and does nothing on any other store. The start page and the Boost skill show the schedule line.

### 🔧 Changed

- **`Support\MigrationLocks` is internal.** It has shipped since 0.1.0 as public API, for a migration of the package that alters a table and is published into an application. No migration of this package calls it, so the class leaves the public API: an application that calls it from a migration of its own keeps working until a later release changes or removes it.
- **The WireKit view of the screen stands each of its parts in a card.** The form, the list of tokens and the quickstart followed each other in one column, while WireKit lays out each part of a settings page in a card with a head, and a host's settings page showed the screen between such cards. Each part stands in a card now, its head with an icon, the name of the part and one sentence on what it is for, from the new lines under `screen.parts`. A host that published the WireKit view takes the cards from the view of the package.
- **A token is limited to at most 50 addresses and networks.** Every request with a limited token reads its whole list and checks the address against each entry, and the list had no limit but the size of a request, so whoever minted a token decided what each of its requests cost. A mint and `restrict()` of `TokenNetworks` refuse a longer list now with a `MintRefused` whose reason is `too_many_networks` and whose `limit` names how many a token may have, `minting.max_networks_per_token` or `SANCTUM_HARDENING_MAX_NETWORKS_PER_TOKEN`. The screen says the limit on its status line and marks the field of the networks. A second copy of an entry counts once.

  **Upgrade:** a token that holds more entries keeps them until its networks are changed.

### ⚡ Performance

- **The screen reads the latest requests of all the tokens it lists in one query.** It read them with a query for each token, so a holder with twenty tokens, and every expired one not pruned yet, paid twenty more queries on every render, and Livewire renders the screen again after every action. `latestOf()` of `TokenUses` reads them for all the tokens it is given in one query now, five of each, the newest first, so a render costs as many queries with twenty tokens as with one.

### 🐛 Fixed

- **An ability whose name ends in a line feed is refused.** The catalog refused the wildcard and a name with a space or a comma in it, and let a line feed at the end through, so `define()` took such a name, and an entry of `abilities` or `reserved` that carried one, such as a name read from an environment variable with its line end, stood in the catalog under a name no check of a token asks for. The screen offered it, and a token minted with it answered no for the ability it was meant to grant. `define()` now refuses such a name with an `AbilityRefused` whose reason is `malformed`, and the configuration's entry is left out like any other entry that names no ability.
- **`latestOf()` of `TokenUses` declares its keys as PHP holds them.** It declared every key a string, while the key of a token whose key is a number, as Sanctum's are, comes back as an integer key, so a host's static analysis took that integer for a string and could not see a call that a string parameter refuses under `strict_types`.
- **`sanctum-hardening:send-alerts` goes on past a mail the transport refuses.** One refused mail, for an address from old data the transport rejects or a recipient the mail service has blocked, ended the whole run, and since its token was not recorded as mailed, every later run stopped at the same token: the tokens after it and every alert after a silence were never mailed again. The command now reports the exception to the application's exception handler, mails the next token, and ends with exit code 1 and the number of mails it could not send. The refused mail is tried again in the next run, and `TokenAlerts::send()` counts it under `failed`.
- **The screen says a refused name on its status line.** An empty name, or one longer than 255 characters, was refused by a check of the screen's own before the status line was set, so the line kept what it said before, such as "The token was created." after a mint, and in the plain view a screen reader announced nothing. The name now takes the way of every other refusal: the status line says it and the field is marked as invalid. The message under the field is the package's line in the reader's language now, "Give the token a name of at most 255 characters." in English, rather than Laravel's validation message.
- **The plain view of the screen fits a phone.** Its list of tokens, six columns wide, and the example request of the quickstart, a single line that does not wrap, were wider than a phone's screen, so a page that embedded the plain view scrolled sideways there unless the host's own styles held both. The list now scrolls sideways in an area of its own, which a keyboard reaches, the example request wraps, and a new token stands in a field as wide as the screen.
- **The quickstart of the plain view ends its first sentence.** 0.4.1 ended it with a period after the address in the WireKit view only, so a host without WireKit, or with `ui.variant` set to `plain`, still showed the sentence stop at the address. Both views end it now.
- **The token screen names one landmark.** In the WireKit view the list of tokens was a landmark of its own under the screen's name, "API tokens", so a screen reader listed that name twice among the landmarks of the page, and in both views the quickstart stood in an `aside` inside the screen's section, which a screen reader announces as content beside the page. The list is no landmark of its own now and stays reachable by keyboard, and the quickstart is a part of the screen under its heading. A host that published the views makes both changes in its copies.
- **Revoking a token keeps the keyboard's place in the list.** The row of a revoked token left the list with the button that had the focus, so the focus fell back to the start of the page, and a person on a keyboard or a screen reader lost their place after every revocation. The focus moves to the revoke button of the token below now, to the one of the token above where the last token went, and to the screen's heading once the list is empty. A host that published the views gives each revoke button `data-sanctum-hardening-revoke` with the token's key and the heading `tabindex="-1"`, as the views of the package do.
- **A password timeout of `0` lets the one mint after a confirmation through.** `minting.password_timeout` at `0` is meant to ask for the password before every mint, and let a mint through only in the second of the confirmation itself, so the screen, which confirms and mints in two requests, went round between the password field and the refusal and minted nothing. A confirmation now covers the one mint made within five minutes of it, and that mint spends it, also for a request of the same session sent at the same moment; the next mint asks for the password again. The confirmation stays in the session for the application's other routes behind `password.confirm`.
- **Two screens on one page keep their ids apart.** Every id the views wrote was the same in each screen, so with the screen of the user and the one of a workspace on one page, each label of the second form named the field of the first, the fields of the second had no label, and both sections took their name from the first heading. Every id ends in the id of the Livewire component now. **Upgrade:** a stylesheet that selected an element of the screen by its id selects it by its place inside `[data-sanctum-hardening-view]`, and a host that published the views writes each id through `$domId()`, as the views of the package do.
- **Laravel's password timeout counts the way `password.confirm` reads it.** Where `minting.password_timeout` is null, a mint takes Laravel's `auth.password_timeout`, and Laravel reads `0`, an empty value and null there as three hours. An empty line `AUTH_PASSWORD_TIMEOUT=` in the `.env` gives an empty value. The package refused every mint under an empty value or null, and under `0` let a mint through only in the second of the confirmation, while the application's routes behind `password.confirm` took the same confirmation for three hours. All three mean three hours for a mint now; `minting.password_timeout` itself is read as before.
- **The screen names the entry of the networks it refuses.** A list of networks with one entry that is no address and no network was refused with "A token cannot be limited to one of these addresses or networks.", so a person who typed ten lines checked all ten, and the field was not marked. The status line names the entry now, `203.0.113.300` for instance, and in both views the field is marked as invalid and points to the message under it. `MintRefused` carries the entry in `network`. **Upgrade:** a host that published the translations gives `screen.refused.network` the placeholder `:network`, and one that published the plain view marks the field of the networks as the view of the package does.
- **The switch silences a cached route as well.** `SANCTUM_HARDENING_ENABLED=false` was read only where `SanctumHardening::routes()` registers the routes, and a host that caches its routes loads the table it cached instead, so there the API kept answering after the switch went off, until the routes were cached again after the configuration. Every route of `SanctumHardening::routes()` reads the switch on each request now, through the middleware `Pushery\SanctumHardening\Http\EnsureApiIsEnabled`, which comes before the token guard and answers the `404` of a route that is not there while the API is off. With a cached configuration the switch takes effect once the configuration is cached again; `php artisan optimize` caches it and then the routes.
- **The mail after a silence waits for a last use Sanctum writes.** Sanctum writes `last_used_at` only while its setting `sanctum.last_used_at` is on, and the package read the column as though it always did: with the setting off, the holder of a token used every day was mailed that it had never been used, with the advice to revoke it, and the screen showed every token as never used. While Sanctum writes no last use, `sanctum-hardening:send-alerts` sends no mail after a silence and says why, the screen shows the last use as "Not recorded", and `sanctum-hardening:doctor` reports the alert where it is switched on. **Upgrade:** on a host with `sanctum.last_used_at` off, a deploy step that runs the doctor fails until `alerts.inactive.enabled` is switched off or Sanctum writes the last use again, and a host that published the views shows the line as the views of the package do, from `$lastUseRecorded`.
- **The screen mints after a person goes back to the default lifetime.** In the plain view, choosing another lifetime and then the first one again sent the empty text of that option with the mint, which Livewire could not put into the screen's number of days, so the mint ended in Livewire's error dialog, and so did every later one until the page was loaded again. The screen takes the lifetime as the text a select sends now, reads the empty text as the default and a whole number as its days, and says that any other text is no lifetime it offers. The plain view sends the choice as a number as well, and a host's published copy of it needs no change.
- **A token named longer than 255 characters can be revoked.** Sanctum keeps a token's name as text, and the record of a revocation keeps it in a column of 255 characters, so revoking a token the application had named longer through `createToken()` failed on PostgreSQL and on MySQL in strict mode: the record was refused, the expiry was never set, and the token stayed valid. The record keeps as much of the name as its column holds now, 255 characters unless the application set another length with `Schema::defaultStringLength()`, and the token is revoked.
- **A change of a token's networks that fails keeps the old ones.** `restrict()` of `TokenNetworks` deleted the old list and wrote the new one in two statements, each committed on its own, and a token without a list is accepted from any address, so a lost connection or a timeout between the two left a token minted before, whose plain text its holder has, without any limit. Both go in one transaction now, and a change that fails leaves the token with the networks it had.
- **A token revoked a second time keeps its first revocation.** `revoke()` of `TokenRevocations` recorded a revocation without looking for one, and the record is keyed by the token, so revoking a token that was revoked before failed with the database's error for a duplicate key. A loop that revoked every token of a user stopped at the first one revoked before and left the tokens after it valid, and of two screens that revoked the same token at once, the second ended in the same error. A second revocation changes nothing now: the record of the first, with the user who revoked it and the time, stays, the token keeps the expiry it was given then, and `revoke()` answers `false`, where it answers `true` for a token it revoked. `PersonalTokens::revoke()` answers `false` for a token another request revoked after it read the list.
- **The screen renders its plain view on a WireKit older than 2.67.0.** The WireKit view lists the latest requests of a token through the `items` of WireKit's list, which WireKit takes from 2.67.0 on, and `ui.variant` at `auto` chose that view wherever WireKit was installed, so on an older WireKit the screen worked after the installation and broke once a token had made its first request. `auto` takes the WireKit view now where Composer reports WireKit 2.67.0 or later, and the plain view below it; `wirekit` renders the WireKit view whatever the version.
- **An alert goes out once on PostgreSQL in whatever time zone the database session runs.** The package keeps its moments there with their zone, and Laravel binds a moment without an offset, which PostgreSQL reads in the zone of the connection's session; Laravel sets that zone only where the connection names a `timezone`, and the connection Laravel ships names none. In a session of another zone than the application's, every moment was stored as far from itself as the two zones stand apart, so the occasion of an alert never matched the expiry or the last use Sanctum holds, and every run of `sanctum-hardening:send-alerts` mailed the same alerts again, daily under the documented schedule. A revocation read back as far off. The package writes its moments with their offset on PostgreSQL now, so they hold in any zone, and `sanctum-hardening:doctor` warns where the session runs in another zone than the application, without failing for it. A moment stored before keeps its shift, so a due alert is mailed once more and then recorded right.
- **The alerts and the prunes run once at a time without a flag.** The documentation said `sanctum-hardening:send-alerts` and the three prunes run once at a time, and they did only with `--isolated`, which the lines it scheduled them with do not pass. Two runs at once, from the schedulers of two servers for instance, each read the alerts mailed before either recorded its own, so the holder of a token got every alert that was due twice. The four commands take their lock without the flag now, and a run that starts while another is still going ends at once with exit code 0. The lock lives in the application's default cache store, so servers that run the scheduler together need a store they share, such as Redis or the database.
- **The line that says until when a replaced token works stays on one line in the WireKit view.** A date broken over two lines reads as two values, and the token list kept the other dates of a row on one line already.

### 🔒 Security

- **The alert mails set a token's name into their text as text.** The mails before a token expires and after it has gone unused put the name somebody typed, and the start of the secret, into their Markdown as it stood, so a name written as a link, `[Renew](https://example.com)`, arrived as a link in a mail the application sent, and a name written as an image loaded that image. Both now arrive as the characters that were typed. The subject names the token as before, since a subject is no Markdown.
- **The password confirmation counts an attempt before it reads the password.** `confirmPassword()` of `PersonalTokens`, which the screen asks for the password through, read the count of wrong passwords before the slow hash and raised it after, and the requests of one session run at once, so a burst of requests sent together had as many attempts as it had requests rather than five a minute. Every attempt is counted before the password is read now, the right password clears the count, and the sixth attempt within a minute is refused unread however the attempts arrive.
- **The password confirmation counts the wrong passwords of a user from every address together.** It allowed five wrong passwords a minute for the user and the client's address, while a session is bound to no address, so whoever held a session could try five passwords a minute from every address they could send from, each address of an IPv6 network on its own. A guessed password confirms the session for every route of the host behind `password.confirm` as well. The five a minute are the user's now, from every address and session together, and only a session of the user reaches that count.
- **The password confirmation keeps the address out of its cache key.** `PersonalTokens::confirmPassword()`, which the screen asks for the password through, counted wrong passwords under a key that ended in the client's address in plain text, and error trackers and the monitors of a cache store record cache keys. The key names the user alone now, since the count is the user's from every address.
- **The limiter counts a request nobody is signed in for by the /64 of an IPv6 address.** It counted such a request by its full address, and a single line or host is given a whole /64 of IPv6 addresses, so a client that sent each request from another of them drew a fresh count every time and never met the limit. This reached a route of the application's own behind `throttle:sanctum-hardening` that lets a guest in, and the routes of a host whose `routes.middleware` leaves out `auth:sanctum`; the package's routes answer a guest with `401` before the limiter counts. An IPv6 address counts by its /64 now, and an IPv4 address, also one mapped into IPv6, as before.
- **The token screen keeps the plain text of a new token and the typed password out of the page.** Both were public properties of the Livewire component, so the snapshot Livewire writes into the page held them, and the browser sent them back with its next request: the plain text of a new token, which Sanctum stores only as a hash, with the action after its mint, and a password typed into the confirmation field with every action until Confirm was pressed. A tool that records request bodies, a request watcher or an error report with the payload, kept both. The plain text now exists for the answer to its mint alone, and the password field is emptied before every answer, also where the password went to the server with another action. Published views keep `$plainTextToken` as before.

## [0.1.0] - 2026-11-08

### ✨ Added

- **An ability catalog without a wildcard.** Every ability a token can carry is named in `sanctum-hardening.abilities` or with `AbilityCatalog::define()`, and minting refuses the wildcard, an unknown ability and none at all with an `AbilityRefused`. A reserved ability is minted only by the application's own code, and the self-service screen neither lists nor revokes a token that carries one. `sanctum-hardening:doctor` names the tokens minted outside the package with the wildcard or an unknown ability.
- **Minting with limits.** `PersonalTokens::mint()` mints for the signed-in user behind a password confirmed within the timeout, at most `max_tokens_per_user` tokens that have not expired and `per_minute` mints a minute, one at a time, with a lifetime from `minting.lifetimes`. A resolver of the application can lower the limit, and `mintForSystem()` mints for the application's own code. Each token keeps the first twelve characters of its secret, so a person can tell their tokens apart.
- **Tokens of a workspace.** `PersonalTokens::mintFor()` mints a token that belongs to a tokenable other than the signed-in user, a workspace for instance, under the rules of `mint()` counted for that tokenable and behind the signed-in user's confirmed password. The application decides who may do so with the Gate ability `manage-tokens`, named by `tokenable_ability`, or a policy method `manageTokens()`, and where it defines neither, every such mint is refused as `not_allowed`. `listFor()` and `revoke()` take the tokenable as their last argument.
- **Throttling in two stages.** The API registered with `SanctumHardening::routes()` runs behind a limit per token and one per user over all of their tokens, and a request over either is answered with `429` and `Retry-After` as a problem document.
- **A switch that removes the API.** With `SANCTUM_HARDENING_ENABLED=false`, `SanctumHardening::routes()` registers no route at all.
- **An optional self-service screen.** `<livewire:sanctum-hardening.tokens />` mints, lists and revokes the signed-in user's tokens through `PersonalTokens`, shows a new token's plain text once and never offers or lists a reserved ability, in a WireKit view and a plain one chosen by `ui.variant`. It shows when a token expires and when it was last used in the reader's language, with "Uhr" after a German clock time.
- **The prefixes of deleted tokens are pruned.** `sanctum-hardening:prune-prefixes` forgets the prefix of every token that no longer exists, the ones a query deleted included, as `sanctum:prune-expired` deletes them. Schedule it beside Sanctum's prune.
- **The last use of a token written once a minute.** Sanctum's write of `last_used_at` on every request goes through once every `last_used_at.every` seconds.
